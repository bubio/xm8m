## 1. この基準の目的とブランチ境界

正常に使えている媒体操作を、本番処理を呼ぶ自動試験で保護してから内部設計を置き換える。
ユーザーの指示により、この基準をコミット・pushしたことを確認した後で別ブランチを作り、設計変更はそのブランチだけで行う。
元ブランチへ状態機械の置換を混ぜない。pushできない場合も、完了したと報告して先へ進まない。

## 2. 本番を通す試験境界

`Tests/ra_app_media_integration_test.cpp`は製品と同じ`App`、`DiskManager`、PC-8801MA VM、FDC、D88 parser、RA Library／MediaStore／Serviceをリンクする。
Appの公開メニュー入口、およびD&Dの媒体処理・reset完了処理を実際に呼ぶ。policyの結果だけを照合する試験ではない。

差し替えるのはEMU_SDLのホスト境界とRAのHTTP／認証保存だけである。SDLウィンドウを開かず、ユーザーのROM・設定・RA DB・Keychain・実ネットワークを使わない。
各実行で一意の一時ディレクトリを作り、生成D88と一時DBを置く。成功終了時にそのディレクトリだけを削除する。

本番の変更は以下のみ。媒体判定・処理順序は変更しない。

- Appへテスト接続用friendを一つ追加。
- `OnDropFile`の成功時reset処理を、その内容を保って`FinishDroppedDiskOpen`へ抽出。製品とテストが同じ処理を呼ぶ。

reset回数は実VMへ追加した試験用DEVICEで観測する。現VMは一回のresetで全DEVICEを二度resetするため、それを一回として数える。製品VMへ試験用カウンタを追加しない。

## 3. 固定した基本動作

| 条件・操作 | 観測する結果 |
|---|---|
| RA OFF、RA ONでログイン不能 | Drive 1／2の単独Open、他Drive維持、実FDCの挿入 |
| 複数D88 | 3種類の異なるhashの生成媒体を後続交換できる |
| 3bank D88 | bank 2の指定とbank切替。最初の2bankだけに限定しない |
| RA OFFのbank切替 | 現行の32フレームの交換待ち後に実FDCへ反映。即時mountを要求しない |
| 両Drive指定 | 選択したpath・bankを両Driveへ反映 |
| Eject | 各Driveの管理状態と実FDCの双方から取り出される |
| raw D88／bank指定M3UのD&D | 既存Drive割当、単一D88時のDrive 2 Eject、成功後のVM reset一回 |
| 両Driveのローカル検査失敗 | 一方のbank範囲不正で、旧両Drive構成・reset回数を維持 |
| RAの未登録応答 | Casual／Hardcoreの両方でOfflineとなり、Open・交換・Ejectを続けられる |
| Offline後に別Drive 1をmountして通常reset | 新しいStartingを経由し、登録応答でActiveになる。ロード完了時の追加VM resetなし |
| Activeの同一hash D&D | sessionを維持し、VM resetは一回 |

RA ONのpathは元D88でなく対応するworking copyであることも照合する。
RA OFFではRA Library・Service自体を用意しないため、それらの存在が通常操作の条件になっていないことを確認する。

### 2026-09-08: 非同期anchorのVM適用・復元を共通化

前段の試験追加・M3U修正は`bce49caf2154c4e2f2cd7804b864318e4cd0127a`として設計変更ブランチへpush済み。そのcommitから、次の構造変更を分離した。

- `Source/UI/diskmounttargets.h`に`DiskMountTargets`を追加。DriveごとのKeep／Eject／Mount(path, bank)を値として保持し、Drive 1 → Drive 2の順に適用する。Keepはsnapshot／復元対象からも外す。
- これは48のPreparedMediaが持つVM適用先の部分であり、requestId・起動意図・reset・RA hashを持つ完成したMediaRequest／Coordinatorではない。ローカル検査、RA、profile保存、resetは呼出し側の責務を維持する。
- `BeginRaMediaChange`で既存の単独／raw pair指定を一度だけ適用先へ変換し、対象Driveのsnapshotを保持する。非同期状態に`open_pair`／`target_banks`／Drive 1用の個別snapshotを重ねて持たない。
- `ProcessRaMediaChange`の成功とRA拒否後のローカルmountが同じ`Apply`を使う。Drive 2検証失敗とDrive 1変更失敗のOffline処理を`CommitRaMediaChangeOffline`へ共通化。RA終了が旧transactionを消すため、その直前に要求を値で退避する。
- VM失敗後は同じ対象snapshotを復元し、既存のRA rollbackへ進む。RA OFF／非対応ゲームの許可条件、必要なreset、profile保存の必須／通知の区別は変更しない。失敗通知の表記は共通の「VM rejected … media」にまとめた。
- Library STARTの同期mountも同じ`Apply`を利用する。Libraryの検証・非同期起動・保存・resetの順序は維持する。

追加した観測:

1. Activeの3bank D88からraw D&Dでbank 0/1へ交換。Drive 2検証待機中に旧Drive・RA hash・reset回数を維持し、成功でも未登録応答でも要求した二Driveをmount、reset一回（Hardcoreで本番Appを実行）。
