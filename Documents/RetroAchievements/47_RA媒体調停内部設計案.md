# RA媒体調停 内部設計案

- 作成日: 2026-09-06
- 対象: `a8d73aa`時点の実装
- 状態: **設計案。実装変更は未着手**

## 1. 位置づけ

本書は、[45_RA統一媒体状態仕様と検証基準.md](45_RA統一媒体状態仕様と検証基準.md)を実現するための内部設計案である。
媒体動作の唯一の規範は45、検証運用は[46_RA統一媒体動作確認運用手順.md](46_RA統一媒体動作確認運用手順.md)とする。
本書は新しい媒体仕様、操作制限、受入基準を追加しない。43・44およびレビュー上の仮説を仕様の根拠にしない。

状態・イベント・遷移条件・副作用・完了条件の具体化は、[48_RA媒体状態機械詳細設計.md](48_RA媒体状態機械詳細設計.md)と同書からリンクする生成遷移表を参照する。
本書は構造・移行方針、48はその詳細設計である。媒体仕様は引き続き45のみとする。

現在、基本動作はユーザーのmacOSで正しく動いている。この動作を維持しながら、同じ処理の重複と呼出し順への依存を減らし、本番の調停処理を自動試験できる構造へ整理する。
不具合候補の修正と、正常動作を変えない構造整理は区別する。

ユーザーが明示した既存動作として、**D&Dによるディスク交換は必ずresetを伴う**。
非同期処理でも要求を失わず、VM commit後に一度実行する。ゲーム中の交換であることを理由に、このresetを省略しない。

## 2. 維持する動作と仕様の対応

| 維持する動作 | 根拠 | 内部設計での扱い |
|---|---|---|
| CasualとHardcoreの媒体判定を共通にする | 45 §1・§2、AM-01 | 媒体計画とHardcore操作ガードを分離する |
| 別D88と同一D88のbankを、選択bankのhashで判定する | 45 §1・§3、AM-02 | 入口で媒体指定を正規化する |
| Drive 1だけ、Drive 2だけ、両Driveを操作できる | 45 §3・§3.2、AM-11 | Driveごとに変更内容を指定する |
| RA非対応・未登録・照会不能でもローカルmountできる | 45 §1・§3・§5、AM-03・05・07 | RA評価停止後も、同じ媒体要求を完了まで保持する |
| ローカル検査失敗では旧Drive構成とsessionを保つ | 45 §1・§3.2・§5 | 必要な準備を副作用より前にまとめる |
| 同一ゲームの二Drive交換ではDrive 2検証を先に行う | 45 §3.2、AM-11・12 | 一要求の計画に順序を持たせる |
| 新anchorは識別後、そのGame IDでDrive 2を検証する | 45 §3.2、AM-11・12 | 起動も同じ要求の進行処理を使う |
| resetと再識別はcommit後の共通規則に従う | 45 §3.3・§5、AM-03・11 | 完了処理を一箇所にする |
| 競合する別要求にはBusyを返す | 45 §3、AM-09 | 受付時に判定し、既存要求を保持する |
| session内の検証cache、通信断中の評価・outboxを維持する | 45 §2・§3.1・§4、AM-06・08・10 | 既存Serviceとsessionの責務を保持する |
| RA OFFでは通常の媒体操作をRAに依存させない | ユーザー確認、46 GU-01 | RA準備・識別・登録を通らずローカル操作へ進む |

ゲームに属する媒体の一覧と、現在の二つのDriveへの割当は別のデータである。
複数D88、任意bank、M3U内の選択媒体を扱い、二枚組やbank 0/1だけの設計にしない。
Open Bothのbank割当、M3Uの選択方法、Library profile、CLI、D&Dの既存入力規則を保つ。

## 3. 構造の変更方針

媒体要求を受け付けてから、必要な非同期処理、VM commit、reset、完了通知までを一つの`MediaCoordinator`が所有する。
以下の名称は実装時の候補であり、新しい汎用フレームワークを導入する提案ではない。

```text
既存のmenu・bank・Open Both・Library・M3U・CLI・D&D
                    │ MediaRequest
                    ▼
             MediaCoordinator
             ├─ ローカル準備   → 既存Probe / RaMediaStore
             ├─ RA処理        → 既存RaService
             └─ commit/reset  → 既存DiskManager / VMへの薄いアダプタ
                    │ 完了結果・表示用snapshot
                    ▼
                 App / Menu
```

`RaMediaStore`、`RaLibrary`、`RaService`、D88 parser、Hardcore policy、outboxは再利用する。
DB schemaの変更、媒体の再登録・移行、UIの操作方法変更を前提にしない。
まず媒体調停だけをAppから抽出し、アプリ全体の再設計へ広げない。

### 3.1 各処理の責務

| 処理 | 所有するもの | 所有しないもの |
|---|---|---|
| 入口の変換 | 既存入力からDrive・path・bank・reset要求を作る | RA成功可否による独自mount／restore |
| ローカル準備 | D88検査、RA ON時の作業コピーとhash解決 | RA session停止、VM変更 |
| 媒体計画 | 45 §3の判断と§3.2の実行順序 | SDL、HTTP実行、ファイル操作 |
| Coordinator | 進行中要求、phase、完了、session遷移の調停 | メニュー再構築、DB実装、HTTP実装 |
| VMアダプタ | 対象Driveのsnapshot、適用、復元、VM reset | RA対応可否の判定 |
| RaService | RA API、応答、既存cache、outbox | UI入口別のmountやVM reset |
| App / Menu | 入力・表示・既存実行ループへの接続 | 受付後の独自reset、非同期結果別の媒体復元 |

session状態は45の`Ready / Starting / Active / ActiveDisconnected / Offline`を維持する。
最終形ではCoordinatorが媒体に伴う遷移を管理し、Appはそのsnapshotを参照する。
RaServiceのロード・通信状態は外部処理の結果として扱い、AppとCoordinatorがそれぞれ別のsession状態を更新する構造にしない。
Hardcore選択と禁止操作の判定は、既存policyを通してこのsession状態を参照する。

## 4. 要求と準備済みデータ

### 4.1 MediaRequest

要求は次の情報だけを持つ。

- Driveごとの`Keep / Eject / Mount(path, bank)`。
- 既存操作が要求するresetの情報。D&Dは必須として記録する。
- 通常の媒体交換か、Library STARTなどの明示的な新規起動かの意図。同じhashでも新規起動の既存cold bootを失わない。
- 応答と完了を対応させる要求ID。

ゲームの全媒体一覧や、UI画面の状態をtransactionへ持ち込まない。
片側Openは他方を`Keep`、両側交換は二つの`Mount`、一枚のD&Dで他方を閉じる既存操作は`Mount + Eject`として表す。
M3U全体に何枚含まれていても、今回選択したDriveへの操作を一要求へ変換する。

resetの要求情報は、45 §3.3に従う完了方法と区別する。
「reset要求なし」だけを理由に、45が要求する新anchor起動時のresetを省略しない。
逆に、共通化したという理由で全ディスク操作へresetを追加しない。

### 4.2 準備

1. 競合する別要求があれば45 §3に従ってBusyを返す。
2. 今回の操作対象と、復元に必要な変更前snapshotを確定する。
3. `Mount`対象のD88とbankをローカル検査する。
4. RA ONの場合だけ、対象の作業コピー・登録情報・選択bankのhashを解決する。
5. 二ドライブ要求は、両方の準備に成功してからRA sessionまたはVMを変更する。

RA OFFでは4を実行しない。RAライブラリの初期化成功を通常のOpen・bank切替・Ejectの条件にしない。
RA ON時の既存の原本保護は維持し、準備失敗を原本への直接書込みで回避しない。

`Keep`対象は変更しない。単独Drive操作のために、他Driveの再mount・ライブラリ再登録を要求しない。
Library起動の入力は選択profileから作り、現在mount中の媒体をその起動媒体へ混ぜない。

### 4.3 identity

準備済み媒体は、少なくともpath、bank、選択bankのRA hash、ローカル登録IDを区別して持つ。
ローカルgame IDとRA Game IDは別の意味として扱う。
45 §3の「同じGame ID」の判定へ、ファイル名・同じコンテナ・ローカル登録先の一致だけを渡さない。
照会が必要な関係はRaServiceの結果で確定し、照会不能の処理も45の表に従う。

## 5. 一要求の進行

### 5.1 phase

既存のAnchor用・Auxiliary用に分かれた進行関数を、一つの進行処理へまとめる。
phaseの正確な一覧と遷移は[48の生成遷移表](48_RA媒体状態機械遷移表.generated.md)で管理する。
従来の概略phaseを、ローカル準備、Game ID照会、識別、補助媒体検証、active media変更、VM適用・復元、reset、再識別の結果イベントに分けて具体化した。
特にFinishへ非同期処理を隠さず、AwaitReset／AwaitReanchor／AwaitPostAuxとして完了まで追跡する。

phaseをUIから直接書き換えない。同期的に終わる段階は同じ呼出し内で進める。
同じ要求を表すための`kind`、`operation`、複数のpendingフラグを重ねず、phaseとその段階に必要なデータで表す。
既存Serviceの処理待ちsnapshotを、別の独立したboolへ複製しない。

Appは通常のservice tickでHTTP結果を取り込んだ後、Coordinatorを一度進行させる。
RAのロード成功だけでAppが独自に要求を完了させない。二ドライブ起動は、45 §3.2が要求する後続検証とcommitまで同じ要求に属する。

### 5.2 代表的な経路

| 経路 | 順序 |
|---|---|
| RA OFF／Offlineのローカル操作 | 準備 → CommitVm → Finish |
| Drive 1の同一hash | 準備 → ローカルcommit → Finish、session継続 |
| Drive 2の検証済みhash | 準備 → ローカルcommit → Finish、active hash不変 |
| 同一RAゲームの二Drive交換 | 両Drive準備 → 必要なDrive 2検証 → Drive 1 active media変更 → CommitVm → Finish |
| 新anchorを含む二Drive起動 | 両Drive準備 → anchor識別 → 必要なDrive 2検証 → CommitVm → Finish |
| 未登録・照会不能によるfallback | 準備済み要求を保持 → RA評価停止／Offline → CommitVm → Finish |

表は実行の構造を示すもので、判定条件を置き換えない。通信断中のDrive 1／2の違い、Ready／Offlineの違いは45 §3をそのまま実装する。
RA評価を継続できないことを、ローカルに有効なmount要求の拒否へ変換しない。
Offlineへの移行処理は、未完了要求やそのreset情報を消さない。

### 5.3 BusyとEject

同じ二ドライブ要求の二枚目を、新たなSubmitとして開始しない。
別の競合要求には45 §3・AM-09のBusyを返し、自動queueや既存要求の自動取消しは導入しない。

Ejectも同じ受付境界へ渡すが、媒体識別のAPIは呼ばない。
RA OFFおよび非対応ゲームの通常Ejectを維持する。Pending時に独立して許可されるEjectは45 §3の例外として既存経路を試験で固定し、共通化の際に一律Busyへ変えない。
特に、独立したDrive 2 Ejectを許可したDrive 1単独要求では、完了・復元処理がDrive 2を再挿入しないよう、変更対象のsnapshotだけを使う。

## 6. VM commit・reset・保存

### 6.1 commitと復元

VM適用は一つの実装に集約する。単独操作では対象Driveだけ、両側操作ではDrive 1、Drive 2の順に適用する。
`Keep`は何もしない。適用失敗時は、失敗したDriveを含む変更対象を要求前snapshotへ戻す。
戻した結果も上位へ返し、「復元を試みた」ことを成功と同一視しない。

RA処理は45 §3.2・§5に従う。

- Drive 1 active media変更後のVM失敗では、旧hashへのRA rollbackを試みる。
- RA rollback不能ならOfflineへ移行する。
- Offline fallback後のVM失敗ではDrive構成を復元しても、終了済みsessionを復帰させない。

これはローカル／VM失敗の処理である。RA未登録・照会不能は、前節のOffline commit経路へ渡す。

### 6.2 完了とreset

現在の各入口と非同期完了関数にあるreset処理を、共通の完了経路へ移す。以下のFinishは責務の呼称であり、具体的な状態とイベントは48 §7に従う。
入口は要求を送った後に独自resetしない。これにより、同期・非同期でreset所有者が変わる構造をなくす。

| commit後の状態・操作 | Finishの処理 |
|---|---|
| 同じ要求が開始したStarting | 必要なVM resetを一度行い、識別処理を二重に開始しない |
| Activeの同一sessionを維持 | resetが必要な操作ならVMとRA進捗を一度resetし、sessionを維持する |
| Offlineまたは評価を維持しないlocal mount | 45 §3.3・§5に従う通常resetでは、mount済みDrive 1を再識別する |
| D&Dによるディスク交換 | 上記の状態別規則を使い、成功commit後のresetを必ず一度行う |

最後の行は別のreset実装を追加する意味ではない。D&Dの入力変換が必須resetを記録し、共通Finishが実行する。
他の入口についても、45と現行の正常動作からreset条件を固定する。「ゲーム中だから常にresetなし」「共通入口だから常にresetあり」というルールを作らない。
Offline後の新しい登録Drive 1を、永続的に再識別不可にする状態や禁止フラグも追加しない。

### 6.3 保存と通知

profile保存は、対象構成と保存結果を扱う共通処理へ抽出する。
まず現在の保存タイミングと失敗時の扱いを対応する試験で固定し、単なる抽出で警告化・再試行・rollback条件を変えない。
媒体identityに必要な保存と、最後に使った構成の記録を同じエラーとして混同しない。

受付結果は`Rejected / Pending / Completed`を区別する。
最終結果には、媒体操作の成否、RA状態、保存・復元に関する通知を含める。
`Offlineでmount完了`は媒体操作成功として返し、RA評価を維持した成功と区別して表示できるようにする。
UIの更新はこの結果を受けたAppが行い、CoordinatorからMenuを直接再構築しない。

## 7. 自動試験

### 7.1 最初に固定する基本動作

現在正しく動いている代表ケースを先に固定する。以下は45のAM試験と46のNormal回帰を、具体的な入力と観測結果に展開するための項目である。

| 入力・操作 | 必ず確認する結果 |
|---|---|
| RA OFFで単独Open・bank切替・Eject | 対象Driveのpath・bank・挿入状態、RA呼出し0回、他Drive不変 |
| RA ONで非対応ゲームを使用 | 要求された媒体がmountされ、OfflineでVM実行でき、交換・Ejectを継続できる |
| 複数D88とmulti-bankで同じhash関係を与える | 同じ媒体判定、同じDrive割当 |
| M3Uから片側／両側の媒体を選択 | 選択した媒体・bankだけが要求どおり反映される |
| ゲーム中のDrive 1のみ／Drive 2のみ／両Drive交換 | 操作後の構成とsession、各操作の既存reset条件 |
| raw D88／M3UのD&D | 既存のDrive割当と、commit後のVM reset一回 |
| Library・CLIで二Drive起動 | 要求した構成、識別と検証の順序、起動完了 |
| 非対応Drive 1でOffline後、登録Drive 1へ交換してreset | 新しいStartingから識別する |

媒体には一枚D88、二bank、三bank以上、別ファイル三枚以上のゲーム構成、bank指定付きM3Uを使う。
同時に挿入する二枚以外への後続交換も確認し、「最初の二枚だけ動く」試験にしない。

### 7.2 AM-01〜AM-12との対応

| AM | 主な試験対象 |
|---|---|
| 01・02 | 同じCoordinatorにCasual／Hardcore、別D88／bank入力を渡す |
| 03 | 実際の入口変換 → Coordinator → mount → reset → 再識別 |
| 04〜07 | RaService結果と接続状態に応じた実commit・session遷移 |
| 08 | 既存outbox試験＋媒体fallback後も未送信解除が残ること |
| 09 | 別要求のBusy、既存要求と旧Drive構成の維持 |
| 10 | 既存Hardcore policyと、Coordinatorのsession遷移との接続 |
| 11 | 各入口が生成する要求と、本番の二Drive実行順序・reset・再識別 |
| 12 | VM各Drive失敗、RA rollback、Offline維持 |

AM-04の「失敗」は注入箇所を明示する。RA未登録・照会不能の扱いは45 §3・§3.2・§5に明記されたOffline mount、VM適用失敗は同節の復元として試験化する。
「RA検証失敗なら一律mount拒否」という期待値を追加しない。45に明記のない細かな失敗条件は、基本動作の構造整理へ暗黙に混ぜない。

### 7.3 本番処理を通すテスト境界

CoordinatorはSDL画面や実ネットワークがなくても生成できるものとする。
テストでは本番Coordinatorと入口の変換処理を呼び、外部境界のRA応答、VM操作、時刻だけを制御する。
RaServiceのfake HTTP、MediaStoreの一時DB、実DiskManager/FDCと生成D88の試験も再利用する。

観測するのは最終フラグだけでなく、Driveごとのpath・bank・挿入状態、API呼出し順、reset回数、session状態、VM実行／評価frame数である。
同じ引数でpolicyを二度呼ぶ試験や、入口名だけを変えるループを入口統合試験として扱わない。
入口の比較ではreset要求も確認する。D&Dの必須resetを落として他の入力と同値にする試験を作らない。

基本動作が固定できた後、AM-09・12に必要な遅延応答、各Driveの適用失敗、rollback失敗を追加する。
過去レビューの不具合候補は、45の該当条項を示す再現試験で判定する。未再現の指摘を新しい仕様や一律ガードの根拠にしない。

## 8. 段階的な移行

| 段階 | 変更 | 次へ進む条件 |
|---|---|---|
| 1. 基準を固定 | 本番処理を呼ぶための最小の外部境界を作り、§7.1の基本動作を記録する | 入力・Drive結果・reset回数を自動観測できる |
| 2. ローカル操作を抽出 | snapshot、準備、VM適用・復元を共通化する | RA OFFとRA非対応ゲームの操作結果を維持する |
| 3. 要求を統一 | Open／bank／Open Both／M3U／CLI／D&D／LibraryをMediaRequestへ正規化する | 片側・両側の割当とD&D reset要求が変わらない |
| 4. 進行処理を集約 | Anchor／Auxiliaryの非同期処理と完了処理をCoordinatorへ移す | AM-03〜12の必要な経路が本番処理で通る |
| 5. 重複を除去 | 入口側restore・reset、重複状態・helperを削除する | 45にない拒否条件やreset条件が増えていない |

各段階の差分は、構造変更と振る舞いの変更を分けてレビューできる単位にする。
明確な仕様不一致を試験で確認した場合は、その失敗試験と修正を独立して示す。
既存処理を別名で並存させ続けず、入口の移行完了時に旧分岐を削除する。

実装変更後は46に従ってRA有効buildの`verify_ra.sh --scope full`を実施する。
GUI・実媒体・実ネットワークの受入はユーザーが行い、自動成功と区別する。
本書だけの変更では、リンクと文書差分を確認する。過去の39件PASSを、新しい設計の実装・検証完了として扱わない。
