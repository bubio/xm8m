## 1. 引継ぎ時に守る前提

現在の基本動作はユーザーのmacOSで確認されている。今回の目的は、正常にmountできる条件を維持し、処理順の重複と暗黙のpending状態をなくすことである。状態機械化を理由に機能や操作制限を変更しない。

特に次を実装担当者の推測で変更しない。

1. RA OFFではRAサービス・DB・ログイン・hash照会をmount／Ejectの前提にしない。通常のローカル媒体検査は行う。
2. RA ONでも未登録、別Game ID、照会不能は媒体拒否にしない。必要なOffline移行後、要求した媒体をmountする。
3. ゲームは別D88ファイル、同一D88内の任意bank、M3Uなどからなり、三枚以上にもなる。同時に使う二Driveとゲームの全媒体一覧を混同しない。
4. ゲーム中にDrive 1だけ、Drive 2だけ、両Driveを交換できる。`Keep`は他Driveを変更しない指定である。
5. **D&Dによるディスク交換は成功commit後に必ず一度resetする。** ゲーム中という理由で省略しない。他の全操作にresetを追加することもない。
6. Casual／Hardcoreで媒体遷移表を分けない。Hardcore禁止操作は45 §2のsession状態から既存policyで導出する。

以下は設計契約である。概念上のCoordinatorに対応する実装はApp内のRunnerアダプタであり、別クラス名ではない。§11に実在するsymbolとホスト側に残した境界を記す。

## 3. 状態の分解と更新の所有者

全体の論理状態は`{session, operation, context}`である。巨大な直積をenumに展開しない。

| 要素 | 内容 |
|---|---|
| session | 45のReady / Starting / Active / ActiveDisconnected / Offline。RA OFFは別の有効設定であり、第六のRA sessionではない |
| operation | JSONで定義する一要求の進行状態。Idleから始まり、完了通知後Idleへ戻る |
| context | 媒体指定、準備済み媒体、復元情報、照会結果、resetの用途など、その状態に必要な値 |

Coordinatorのみが媒体に伴うsession／operation遷移を確定する。Appはsnapshotを読む。RaServiceはAPI処理と結果を所有し、ロード成功を理由にAppが先回りしてActiveへ変更しない。

例えば`AwaitAux`と`Starting`は同時に成立する。新anchor識別が成功しても二Drive起動の検証・commit・resetが終わるまで評価を開始しない。一方、既存ゲームの交換では同じ`AwaitAux`でもsessionはActiveまたはActiveDisconnectedのままである。

`Offline`は媒体操作の終端ではない。`EnterOffline`は評価停止、sessionのcache破棄、RAランタイムの終了を行うが、operationと要求・reset情報を消さない。outboxを消さない。

### 3.1 contextの型

| 値 | 契約 |
|---|---|
| Request | requestId、DriveごとのKeep / Eject / Mount(path, bank)、操作のreset要求、起動意図 |
| 起動意図 | 通常の媒体交換 / 明示的な新規起動。LibraryのSTARTは新規起動。同じhashでもSTARTの既存cold bootを失わない。入口名自体をRA判定条件にしない |
| PreparedMedia | 元指定、VMに渡すpath、bank、RA ON時のhashとローカル登録ID。ローカルgame IDはRA Game IDと別の型／フィールド |
| Before | 変更対象Driveのsnapshotと旧RA hash・session世代。KeepのDriveをrestore対象に含めない |
| RaDisposition | Preserve / NewLaunch(launchId, Game ID) / ChangedActive(oldHash, newHash) / Ended。互いに排他的な結果型 |
| ResetDisposition | None / Local / Preserve / ActivateLaunch / Reanchor。Finalizeで一度決め、AwaitResetに保持する |
| ResponseToken | requestId + sessionGeneration + effectSequence。再識別・再照会ごとに新しいsequenceを使う |
| Result | 媒体成功／失敗、現在RA状態、保存・復元結果。Offlineでmountできた結果は媒体成功 |

phaseを別のpending bool群へ複製しない。`ChangedActive`のような履歴は復元に必要なので明示的に保持する。任意のboolを増やすのではなく、可能な組合せを制限した型で表す。

## 4. イベントと副作用の実行規則

遷移関数の形は次のとおり。これは`MediaOperation::Reduce`と`Runner`の契約を示す概念形である。

```text
reduce(current, event) -> {next, effects, optionalCompletion}

cell = table[current.operation][event.kind]
row  = cell.select(eventの有限分岐値)  // 一致は必ず一件
nextを確定 → effectsを指定順で実行 → 結果イベントをqueueへ追加
```

外部処理を待つ間は対応するAwait状態に留まる。HTTP callbackはイベントを配送するだけで、VM・session・transactionを直接変更しない。同期で終わるProbeやVM適用も結果イベントに変換し、reduceへ再入しない。ローカルな連続イベントは同じtick内で処理でき、VMの一frameを段階の間に挟む必要はない。

副作用を開始できなかった場合も、同じ結果イベントの失敗分岐を一回返す。`Begin... == false`を無視して待機を続けない。キャッシュによる同期成功も成功イベントを一回返す。既存HTTPの終了・timeout契約をアダプタへ引き継ぎ、新たな無期限待機を作らない。

表の全セルは次のいずれかになる。

- T番号: 通常の遷移。有限分岐ごとに一意に選択する。
- `B`: 別の競合要求へBusyを返し、進行中要求を保持する。
- `N`: 通信状態だけ更新する。operationは維持する。
- `S`: すでに終了したeffectの遅延・重複結果を捨てる。
- `X`: 定義違反。試験では失敗にする。正規の媒体拒否やOffline fallbackとして処理しない。

古いtokenはディスパッチ前に`Stale`へ分類する。同じtokenなのに想定と異なる結果イベントが来た場合はXであり、「全部無視して安全」とは扱わない。未知のイベントenumも検出する。

各結果にはResponseTokenと以下のpayloadを持たせる。RA結果のhash／Game IDも要求と照合し、別要求の成功を流用しない。失敗理由は表示用文字列だけでなく分類値を保持する。

| イベント群 | 発生元 | 必要なpayload |
|---|---|---|
| Submit | 共通受付 | Request。受付済みの主要求に付け足す形式は禁止 |
| Prepared | ローカル準備アダプタ | 成功時は全対象のPreparedMediaとsnapshot、失敗時は失敗対象と理由 |
| PlanResult / AuxPlan / AdvanceResult | Coordinatorの純粋な判断 | 表に列挙した分岐値。判断したsession世代・対象hashとの対応 |
| ResolveResult | RA照会アダプタ | 問合せhash、返されたRA Game ID（未登録なら0）、結果分類。Same／Otherは現Game IDとの比較結果 |
| LoadResult | 起動アダプタ | launchId、anchor hash、ロード済みRA Game ID、成功／不能。不能には未登録・認証・開始失敗を含む |
| VerifyResult | RA検証アダプタ | hash、期待Game ID、実応答Game ID、成功／別ゲーム・未登録／不能 |
| ChangeResult / RollbackResult | RA変更アダプタ | 変更先hash、対象Game ID、成功／不能。成功はAPIの確定結果であって要求受付ではない |
| CommitResult | VM・保存アダプタ | 試行Drive、適用結果、必須保存結果、通知のみの保存結果 |
| RestoreResult | VMアダプタ | Driveごとの実復元結果。全対象復元時だけrestored |
| RollbackPlan / FinishPlan | Coordinatorの純粋な判断 | 表に列挙した分岐値。復元成否やResetDispositionの元データもcontextに保持 |
| ResetDone | resetアダプタ | 実行したResetDisposition、reset後のDrive 1挿入状態。reanchorで未挿入の場合だけnoanchor |
| Connectivity | 既存通信状態の通知 | 現在の接続状態。媒体結果を偽造しない |
| Stale | 共通ディスパッチのtoken照合 | 終了済みtoken。現在のcontextへ結果payloadを適用しない |

VM resetは現行の同期・戻り値なしAPIの契約を使う。新たに失敗を返せるAPIへ変更する場合は、ResetDoneへ失敗を混ぜず、その結果と遷移を追加する。外部APIの契約変更も遷移表の変更としてレビューする。

### 4.1 通信変化と実行順

`Connectivity`はActiveとActiveDisconnectedを45 §4に従って切り替え、既存評価とHardcore制限を保つ。Startingは通信断だけでActiveDisconnectedにならない。Offlineは通信復帰だけでは再開しない。

通信断そのものと実行中APIの結果は区別する。照会開始前には現在の通信可否を確認する。開始後は当該effectの成功／不能イベントで進める。断線時にアダプタが照会不能を確定するなら、そのeffectを終端化し、後発callbackをStaleにする。成功と不能の両方を適用しない。

Drive 1のactive media変更を新規に発行するとき通信不能ならOfflineへ進む。Drive 2は現sessionの検証済みhashなら通信なしで進める。これを同じ「ネットワークがないからBusy」のガードにまとめない。

### 4.2 Busyと独立Eject

正常要求は一回のSubmitで受け付ける。二Drive要求の二枚目を再Submitしない。進行中の競合操作はBusyであり、queue、自動取消し、自動再試行を追加しない。

独立Ejectは**別要求としての小さな同期操作**であり、進行中要求を置き換えない。現行`EjectDiskFromMenu`と`CanEjectRaMedia`の組合せを基準に、Drive 1単独のanchor待機中に、元の要求がKeepとしたDrive 2をEjectできる経路を維持する。Drive 2検証を含む要求中、両Drive要求中、Drive 1に干渉するEjectは独立例外にしない。VM commit／restore／resetの同期区間には割り込ませない。

この受付判定はSubmit前の共通入口で行い、主表のBusyを迂回してmount一般を許可しない。独立Ejectの結果は独立したrequestIdで返す。主要求のsnapshot／restoreはそのDriveを含まないため、後からEjectを取り消す再挿入が起きない。

Idleでも既存sessionがStartingなら競合要求はBusy。新構造への移行中に「operationがIdleだからStartingも空いている」と判断しない。

## 5. 媒体計画の決定規則

主表のPlan、AuxPlan、Advance、FinishPlanなどは内部の純粋な判断結果である。API callbackに都合のよい結果を生成させない。判断の入力と規則を以下に固定する。JSON検証が保証するのは**判断後の分岐**の網羅性であり、この判断関数自体は本番policy試験が必要である。

### 5.1 PrepareとPlan

受付後、変更対象を固定する。MountのD88形式・bank・RA ON時の作業コピー／hashをすべて準備する。Keep／Ejectにhash取得を要求しない。両Driveの準備成功前にはsession停止・RA照会・VM変更を行わない。

Planの上から順に適用し、後続行はそれ以前に該当しない場合だけ評価する。

| 条件 | Plan結果 | 根拠 |
|---|---|---|
| RA OFF | Local | ユーザー確認、46 GU-01 |
| Offlineの通常媒体交換 | Local | 45 §3。必要なreset後の再識別は§7 |
| 明示的な新規起動でDrive 1 Mountあり | Launch。開始不能ならOffline fallback | 現行Library STARTのcold bootを保持、45 §3.2 |
| ReadyでDrive 1 Mountあり | Launch | 45 §3 |
| Ready／Offlineで上記以外 | Local | Drive 2やEjectだけでanchor識別を開始しない |
| Active系でDrive 1 Mountなし、または同一active hash | Existing | Drive 2の必要な判定へ進む |
| Active系でDrive 1が別hash、通信不能 | Fallback | 45 §3。検証済みでもDrive 1は例外なし |
| Active系でDrive 1が別hash、現sessionの同Game ID検証済み | Existing | 後段でDrive 2確認 → media change |
| Active系でDrive 1が別hash、関係不明、通信可能 | Resolve | sessionを変更しないhash→RA Game ID照会 |

Startingでの新規Submitは受付で排除済み。Active系はActive／ActiveDisconnectedを指すが、API発行可否は処理時の接続・認証状態も確認する。永続Library情報だけで「検証済み」を作らない。

Resolve成功は`Same / Other / Unregistered`を区別する。Sameは既存ゲーム交換、Otherは新anchor開始、Unregistered／照会不能はOffline fallback。**Resolveではactive mediaを変更しない。** これにより、未知の別D88でもRA Game IDで順序を決められる。`BeginVerifyMediaHashForGame`のsnapshotは応答Game IDも返す。Appはこれを現Game IDと比較する。ローカルLibrary IDをRA Game IDの代用にしない。

### 5.2 新anchor識別とDrive 2

Launchは旧sessionを終了し、新世代のStartingに移って認証・必要な同期・ゲームロードを開始する。このまとまりは既存RaService／Appの開始処理をアダプタ化する。各前提の開始失敗もLoadResultのUnavailableへ集約し、認証待ちで媒体要求を失わない。

LoadResult成功は「Game IDとRAランタイムが利用可能」を意味し、まだ評価開始ではない。続いてAuxPlanを選ぶ。

| 条件 | AuxPlan |
|---|---|
| Drive 2が空、または既存sessionを維持する要求でDrive 2をKeep | Satisfied |
| 新sessionでDrive 2をKeepし、すでに媒体が挿入されている | mount済みhashを新Game IDで検証 |
| 対象hashが照合対象Game IDのanchor hashと同一、または現世代の同Game ID検証済み | Satisfied |
| 上記以外で照会可能 | Query |
| 上記以外で照会不能 | Fallback |

新規起動では新Game ID、既存交換では現Game IDに対して検証する。別Game ID・未登録・不能はどれもOffline → 同じ要求のcommitへ進む。KeepのDrive 2を再mount・再登録しない。単独操作を勝手に二Drive操作へ拡張しない。

AuxがSatisfied／検証成功ならAdvanceを選ぶ。既存sessionでDrive 1を別hashにする場合だけChangeへ進み、現在照会不能ならFallback。それ以外はCommit。Drive 2の成功をDrive 1 active media変更として扱わない。

## 6. VM適用と復元の契約

Commit effectは対象DriveをDrive 1 → Drive 2の順に適用する小さな同期処理である。Keepは何もしない。二Driveの途中でVM frameを実行しない。結果には成功した／試行したDriveと保存結果を含める。Openがboolを返したことだけで実コアの挿入成功を観測できるか、アダプタ試験で確認する。

適用失敗はRestoreへ進む。失敗したDriveを含む変更対象をsnapshotへ戻し、復元成功／不能を返す。復元後のRA処理は次で決める。

| Restore後 | RollbackPlan |
|---|---|
| VMを復元でき、既存sessionのactive media変更が成功済み | Rollback。旧hashへのRA復元を試行 |
| VM復元不能、または新規session開始済み | End。評価を継続できる構成を保証できないため終了 |
| すでにOffline fallback済み | KeepEnded。旧sessionを復帰させない |
| RAのactive mediaもsessionも変えていない | Preserve。旧sessionを保つ |

RA rollback成功でも媒体要求自体は失敗であり、resetしない。失敗ならOffline。復元不能は結果に明記し、旧構成へ戻ったと報告しない。

profile保存は現在の必須保存／通知だけの保存の区別を保つ。Commitアダプタは必須保存の失敗もCommit失敗として返す。通知だけの保存を新たなrollback条件にしない。抽出前に現行呼出し箇所ごとの期待値を固定する（§11）。

## 7. resetと再識別を表に出す

Finishは任意の処理を隠す関数にしない。FinalizeがFinishPlanを選び、resetが必要ならAwaitResetへ遷移する。

| 状況 | FinishPlan／AwaitResetの用途 |
|---|---|
| 自分の要求が開始したStartingを維持 | ActivateLaunch。VM reset一回 → RA進捗初期化一回 → Active系へ確定 |
| 継続するActive系でreset要求あり | Preserve。VM reset一回 → 同sessionのRA進捗reset一回 |
| RA OFFでreset要求あり | Local。VM resetだけ。RA呼出しなし |
| RA ONで評価を維持せず、通常resetが必要 | Reanchor。VM reset一回 → mount済みDrive 1を識別 |
| それ以外 | None。追加resetなしで完了 |

reset要求はD&D、Library START、起動などの既存操作の意味から作り、RA判定後に消さない。新規launchが成功した場合は45 §3.3に従いresetする。新規起動を試みてfallbackした場合も、その起動のreset必要性を保持する。単なる非対応ゲームのメニュー交換・Ejectに新しいreset義務を追加しない。

ReanchorはResetDone後、Drive 1が挿入されていればAwaitReanchorへ進む。未挿入なら通常resetの非評価状態で完了し、空のhashでloadしない。再識別の成功／不能は主表で扱うため、App側で別の完了判定を走らせない。

二Drive要求がfallbackした後のReanchorでは、**同じ要求に含まれたDrive 2 Mountの検証も再識別のGame IDに結び付ける**。AwaitReanchor → CheckPostAux → AwaitPostAuxとして表に残す。先の検証失敗を忘れてDrive 1のload成功だけで両Drive要求をActiveにしない。これは45 §3.2の二Drive起動条件を、同じ要求のreset後にも維持する設計である。

再識別／再検証失敗ではmount済み構成を維持してOfflineで**完了**する。Commit／Finalizeへ戻さないので、reset → 再識別失敗 → resetの無限循環がない。次の新しい要求やユーザーの通常resetでは、新しい識別を開始できる。永続的な「再識別禁止」フラグを作らない。

通常reset単独は、既存reset処理の所有者からこの共通reset／識別経路へ接続する。媒体を再mountするSubmitへ変換しない。主表のResetDone以後を共有し、その前に媒体操作結果を持つかどうかは完了先で区別する。

## 8. 完了とVM実行

受付結果のRejected（ローカル準備失敗等）／Busy／Pendingと、最終の媒体成功／失敗を区別する。同期でIdleへ戻れば最終結果をその場で返せる。Pendingを返した場合は同じrequestIdへ完了通知を一回だけ送る。

本案ではreset後の再識別も同じ要求の完了までに含める。UIはmount反映を途中snapshotで表示できるが、それを二つ目の完了通知にしない。別の競合要求へのBusy期間を意図せず延ばさないよう、既存Starting期間との比較を試験する。

VMのpause／menu／frame制御は既存ホストの責務を残す。単にoperationがIdleでないという理由だけで新たな全期間pauseを追加しない。ただし次は接続契約として必要である。

- VM commit／restore／resetの同期区間は途中frameを挟まない。
- Starting中はRA評価を行わない。新規起動のframe-zero整合は既存起動ゲートを引き継ぐ。
- RA active hashとVM媒体が一時的に不一致になるmedia change成功〜commit／rollback完了には、その不整合でRA評価を進めない。既存のVM実行ゲートを試験して抽出する。
- ActiveDisconnectedであることだけを理由にVM実行や評価を停止しない。Offline fallback後はローカルゲームを継続できる。

## 10. 設計の境界と未確定事項の扱い

この表が網羅するのは、正規化済み媒体要求、ローカル準備、RA結果、VM適用・復元、必要なresetと再識別、通信変化である。ログインUI、アカウント切替、RA ON/OFF切替、終了、state load全体の状態機械を置換するものではない。

外側のlifecycleがsessionを終える際は、世代を更新して旧callbackを無効化するだけでは不十分である。進行中媒体要求の完了先も必ず処理する。既存の許可・禁止を維持した接続を試験し、必要なlifecycleイベントを表に追加してから旧処理を削除する。未定義イベントをXから黙って無視へ変更して統合済みとしない。取消しはRunnerのCancelとServiceのcallback破棄へ接続する。通常mountを一律禁止する根拠にしない。

45のAM-04には「失敗時は旧構成を維持」とある一方、§1・§3・§3.2・§5は未登録・照会不能のOffline mountを要求している。本案では本文の明示されたRA不能をfallback、VM／必須保存失敗を復元として区別する。実装担当は「失敗」の単語だけでRA不能を拒否に変えない。さらに異なる失敗分類が必要なら、該当API結果と仕様の不一致を具体的に示す。

通常resetの詳細条件、profile保存の失敗方針、独立Eject、Library START、ホストのframe制御は、抽出前の本番試験を移行の必須条件とする。未記載の細かな条件を推測で製品仕様へ追加しない。仕様の確認が必要な問題が生じても、既存の正常ケースの試験と構造抽出は独立して進められる。

### 11.3 同期ホスト境界とreset

既存の同期入口を一律に非同期化しない。RA OFFの遅延bank切替・Eject、Offlineのlocal操作、通常Reset自体は既存ホスト処理を使う。
RA ONの新sessionは一DriveだけでもRunnerがActive確定を所有する。すでにホストがmount／resetした起動は、reset済みの意図で接続し、ResetVm effectではVMを再resetせずResetDoneを返す。
非同期交換のresetはRunnerが実施する。D&D入口の`PlanDroppedReset`は要求がresetを所有していれば何もしない。
通常Resetからの再識別は`BeginRaSessionForMountedDrive1`でStartingへ入り、Runnerのlaunch／D2検証経路で完了する。
Drive 1が空の通常Resetはホスト側で完了するため、生成表のNoAnchorを発行しない。
Connectivityも既存session trackerが所有し、各effect開始時に参照する。表のConnectivityセルはoperationを変更しない。

Library保存では、RAが同じゲームと確認した別importを既存Library IDへ統合する。VM適用後、両Drive要求は構成全体、単独交換はそのDriveのprofileを保存する。
D1／両Driveの必須保存失敗は復元へ進み、補助媒体だけのprofile保存失敗は通知とする。Offline媒体の保存失敗でマウントを拒否しない。
KeepのDriveを新たなmount／restore対象へ追加しない。Startingの評価停止、VM同期区間、Hardcore制限は既存ホストの責務を維持する。
