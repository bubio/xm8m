# RA統一媒体状態仕様と検証基準

基準日: 2026-09-02
状態: **媒体処理の現行規範。実装・受入状況は[49](49_RA状態機械置換前の回帰基準.md)を参照**

この文書はRA ON時のディスク媒体処理と、その回帰試験の唯一の規範である。
旧設計・旧運用手順である

## 1. 目的と原則

RA ON時の媒体処理はCasualとHardcoreで分けない。RA ON用の媒体状態機械を一つだけ持ち、
Hardcoreは実行中sessionに対する禁止操作の集合として扱う。

- `Drive 1` は実行中のRA Game IDを決めるanchorである。異なるhashへ替えるときは、同じ
  Game IDであってもRA active media変更が必要である。
- `Drive 2` は補助媒体である。同じGame IDに属することを確認するが、RA active mediaを
  変更しない。
- 別ファイルをOpenすることと、同一D88の別bankを選ぶことは、媒体判定において同じである。
  どちらも切替先bankのhashで扱う。ファイル名、コンテナ、入口を例外条件にしてはならない。
- Open、Open Both、bank切替、Library、M3U、CLI、drag-and-dropは同じ媒体調停を通す。
- ローカルD88検査（形式、bank範囲、作業コピー）は常にRA照会より先に行う。これが失敗した
  ときはVM、RA session、既存のDrive構成を変更しない。
- 未登録、別Game ID、または照会不能の媒体を理由にディスク操作自体を拒否しない。必要なら
  RA sessionをOfflineへ移行してからローカルmountする。

## 2. モードと状態の分離

媒体policyが参照するsession状態は次だけである。

| session状態 | 意味 | 実績評価 |
|---|---|---|
| `Ready` | RA ONだが実行ゲーム未確定 | 行わない |
| `Starting` | Drive 1 anchorを識別・開始中 | 行わない |
| `Active` | Game IDとactive mediaが確定 | 毎VM frameで行う |
| `ActiveDisconnected` | Activeのまま通信だけ失った状態 | 毎VM frameで継続する |
| `Offline` | 現在のゲームのRA評価を終了した状態 | 行わない |

`Connected`／`Disconnected`はsessionの別仕様ではない。新たなサーバー確認が必要かどうかを
決める入力にすぎない。通信断は、すでにActiveであるゲームの評価やHardcore制限を解除しない。

`Offline`は現在のanchorに対する終端であって、RA ONを無効化する状態ではない。Offline後に新しい
Drive 1媒体をmountして通常resetしたときは、その新しいanchorを改めて識別する。登録ゲームなら
新しい`Starting`へ進み、未登録・照会不能ならOfflineのままローカル実行を続ける。

Casual／Hardcoreは媒体状態ではない。Hardcoreを選択したsessionは`BeginLaunch`から
`Offline`またはsession終了まで、すなわち`Starting`、`Active`、`ActiveDisconnected`の全期間で、
Full Speed、Load State、通常またはautomaticのstate作成、デバッガ、breakpoint、frame step、
メモリ書換え、Pseudo fast diskの実行中変更を禁止する。4MHz／8MHzのCPUクロック切替はcold resetを
伴う通常の構成変更として許可する。デバッグ用の手動Saveは許可する。

## 3. 媒体判定表

次表の「検証済み」は、切替先hashが現在のRA Game IDに属すると信頼できるローカル結果を持つ
ことをいう。通信断中に新しい照会を開始してはならない。

| 現在のsession | 切替先媒体 | Drive 1 | Drive 2 |
|---|---|---|---|
| `Ready`／`Offline` | ローカル検査成功 | `Ready`では識別を開始。識別不能・未登録・通信不能ならOfflineでmount。`Offline`では直接mount | 直接mount。Drive 1の識別を開始しない |
| `Starting`／媒体transaction中 | 既存操作と競合する変更 | 二重の変更を開始しない。旧媒体を維持してbusyを返す | 同左。ただし仕様で独立許可したeject以外は二重変更を開始しない |
| `Active`／`ActiveDisconnected` | 現在のactive hashと同一 | ローカルmountのみ。session継続 | ローカルmountのみ。session継続 |
| `Active`／`ActiveDisconnected` | 同じGame IDの検証済み別hash | 接続中はRA media change成功後にmountしsession継続。通信断中はOfflineへ移行してmount | 直接mountしsession継続。RA active mediaは変更しない |
| `Active`／`ActiveDisconnected` | 同じGame IDだが未検証hash | 接続中は照会・RA media change成功後にmount。通信断中はOfflineへ移行してmount | 接続中は照会成功後にmount。通信断中はOfflineへ移行してmount |
| `Active`／`ActiveDisconnected` | 別Game IDのhash | 接続中は旧sessionを終了し、新しいanchorとして識別を開始。通信断中はOfflineへ移行してmount | Offlineへ移行してmount |
| `Active`／`ActiveDisconnected` | 未登録hash、hash照会失敗、通信不能で未検証 | Offlineへ移行してmount | Offlineへ移行してmount |
| 任意 | ローカル検査失敗 | mountしない。旧Drive構成とsessionを維持 | 同左 |

Drive 1のactive media変更はサーバー側の確定を必要とするため、同じGame IDと事前確認済みでも
通信断中にsessionを維持して切り替えてはならない。一方、Drive 2はactive mediaを変えないため、
同じGame IDとして検証済みのhashなら通信断中でもsessionを維持できる。

### 3.1 検証済みhash cache

検証済みhash cacheは、サーバー成功応答で得た「hash → 現在のRA Game ID」の結果だけを格納する。
cacheは現在のログインアカウントと現在のRA Game IDに束縛し、次のいずれかで必ず破棄する。

- logout、アカウント変更、RA mode OFF、process終了
- `Offline`への移行、session終了、新しいDrive 1 anchor sessionの開始
- server応答が対象hashを別Game IDまたは未登録と示したとき

このcacheを永続化して次回起動や別sessionの検証に使ってはならない。通信断中にHardcore sessionを
維持してDrive 2へmountできるのは、このsessionで得たcacheがある場合だけである。

### 3.2 二ドライブ操作

`Open Both`、複数Driveを含むLibrary profile、M3U、複数Driveを指定するCLIまたはdrag-and-dropは、
一回の**二ドライブ操作**として扱う。内部処理はDrive 1、Drive 2の順で逐次的に進めてよい。
ただし途中失敗で新旧のDrive構成が混在しないよう、変更済みのDriveを以前の構成へ戻す。

| 二ドライブ操作の段階 | 必須挙動 |
|---|---|
| ローカル検査 | 両DriveのD88、bank、作業コピーを先に検査する。どちらかが失敗したら、VM、RA session、両Drive構成を変更しない |
| 既存ゲームの交換 | Drive 1が現在Game IDの別hashへ替わる場合は、Drive 2の照会・検証を先に完了し、その後にDrive 1のRA media changeを行う |
| 新しいDrive 1ゲームの開始 | Drive 1を先に識別して新しいGame IDを確定し、そのGame IDに対してDrive 2を照会・検証する。Drive 2が未登録・別Game ID・照会不能ならOfflineへ移行する |
| 未登録・照会不能 | Drive 1を識別できない場合、または必要なDrive 2検証ができない場合は、既存RA sessionを先にOfflineへ移行し、両Driveをローカルmountする。媒体を理由に要求全体を拒否しない |
| VM mount | Drive 1、Drive 2の順でmountし、必要なcold resetを一度だけ行う。途中で失敗したら、変更済みのDriveを以前の構成へ戻す |
| VM mount失敗後のRA処理 | すでにDrive 1 active mediaを変更済みなら旧hashへのRA rollbackを試みる。rollback不能ならOfflineへ移行する |
| Offline fallback後のVM mount失敗 | 両Driveを以前の構成へ復元するが、終了済みRA sessionは復帰しない。sessionは`Offline`のままとする |

### 3.3 mount後のresetと再識別

媒体要求の入口によって、mount後のresetまたはDrive 1識別の有無を変えてはならない。menu、Open Both、
M3U、CLI、D&Dは、VM commit後に次の共通規則を適用する。

| commit後の状態 | reset後の必須挙動 |
|---|---|
| 同じ要求が開始した`Starting` | VMは一度だけresetする。すでに開始済みの識別を保持し、二重に開始しない |
| `Active`の同一sessionを正しく維持する媒体変更 | VM resetが必要なら進捗を一度だけresetし、sessionを維持する |
| `Offline`、またはRA評価を維持しないlocal mount | 通常resetを通し、RA ONならmount済みDrive 1を新しいanchorとして識別する |

したがって「未登録Drive 1をmountしてOffline → RA登録Drive 1をmount → reset」は、入口にかかわらず
後者の登録ゲームを識別する。D&D専用の直接VM resetでこの再識別を省略してはならない。

## 4. 通信断と解除送信

起動時の識別失敗と、すでにActiveであるゲームの通信断は別問題として扱う。

| 事象 | 必須挙動 |
|---|---|
| Active中に通信断 | `ActiveDisconnected`へ移行する。実績評価とHardcore禁止操作を維持する |
| 通信断中に実績解除 | 送信前に永続outboxへ保存する。送信失敗は解除を捨てず`Pending`として保持する |
| 一時的な送信失敗 | 429、5xx、transport errorは再送対象とする |
| 通信復帰 | outboxを再送し、サーバー成功または「すでに解除済み」を確認してから削除する。成功応答が失われた場合の再送を許容する |
| 恒久的な拒否または応答ID不一致 | `Held`として残し、成功扱いで削除しない |
| 媒体交換でOfflineへ移行 | 実績評価は終了するが、既存outboxは保持し、復帰後に同期する |

したがって「通信断中に未検証媒体へ交換できない」ことは、「通信断前に解除済みの実績を
送信できない」ことを意味しない。

## 5. 実行順序

1. 切替先D88の形式、bank範囲、作業コピーをローカル検査する。
2. 切替先bankからhashを得る。ファイルOpenとbank切替でこの処理を分けない。
3. session状態、Drive役割、hashと現在Game IDの関係、通信可否から上表の結果を一つ選ぶ。二ドライブ
   操作では3.2の順序に従う。
4. RA照会またはDrive 1 media changeが必要なら、VMのDriveを変更せず非同期結果を待つ。
5. 成功時だけVMへcommitし、3.3の共通規則で必要なcold resetを一度だけ行う。
6. Offline fallbackでは、先にRA sessionを終了し、その後にVMへmountする。通常resetが必要なら
   mount済みの新しいDrive 1 anchorを再識別する。
7. VM mount失敗時は旧Drive構成を復元する。RA active media変更後のVM失敗時だけ、旧hashへの
   RA rollbackを試みる。rollback不能ならOfflineへ移行する。Offline fallback後にVM mountが
   失敗して旧Driveを復元しても、終了済みRA sessionを復帰させずOfflineのままとする。

## 6. 必須の自動試験

個別のpure policy testだけで完了としてはならない。menu／D&D／bank切替からVM commitと
session遷移までを通す統合試験を追加し、少なくとも次を機械的に確認する。

| ID | 条件 | 合格条件 |
|---|---|---|
| AM-01 | CasualとHardcoreで同じ媒体入力を与える | 媒体action、mount結果、session遷移が一致する。Hardcore固有の禁止操作だけが異なる |
| AM-02 | 同じhash関係を「別D88 Open」と「同一D88のbank切替」で与える | 同じDrive・通信状態なら同じ媒体actionになる |
| AM-03 | Drive 1で未登録媒体をOpen、D&D、CLI、bank切替から指定。その後RA登録Drive 1媒体へ交換してresetする | 前者はOfflineへ移行してmountし、後者は入口によらず新しい`Starting`からRA識別する。VM開始を妨げない |
| AM-04 | Active中にDrive 1を同一Game IDの別hashへ変更 | 接続中はRA media change成功後に一度だけcommit。失敗時は旧構成を維持 |
| AM-05 | ActiveDisconnected中にDrive 1を別hashへ変更 | Offlineへ移行して対象媒体をmountし、旧sessionが残らない |
| AM-06 | ActiveDisconnected中にDrive 2へ検証済み同一Game ID hashを変更 | sessionを維持し、active hashを変えずmountする |
| AM-07 | ActiveDisconnected中に未検証・未登録・別Game IDの媒体を各Driveへ変更 | Offlineへ移行してmountする。媒体種別・Drive・入口による例外を作らない |
| AM-08 | ActiveDisconnected中に実績解除し、その後AM-05またはAM-07を実行 | 解除要求がoutboxへ残る。成功または既解除確認まで少なくとも一回再送し、応答喪失による重複送信も安全に扱う |
| AM-09 | Pending中に別の媒体操作を行う | 二重transactionを開始せず、旧Drive構成を壊さない |
| AM-10 | Hardcoreの`Starting`と`ActiveDisconnected` | Full Speedを含むHardcore禁止操作が開始直後から通信断中まで同じく拒否される |
| AM-11 | Open Both、複数Drive Library profile、M3U、複数Drive CLI/D&D | 各入口が共通の二ドライブ操作へ正規化され、同じ媒体関係・通信状態ではmount、reset、Drive 1再識別を含む同じ判定と処理順序になる |
| AM-12 | 二ドライブ操作でDrive 1 media change、Drive 2検証、Offline fallback、各DriveのVM mount失敗をそれぞれ注入 | 逐次mount後に途中失敗があれば旧Drive構成を復元し、RA rollbackまたはOffline維持が3.2の表どおりになる |

実媒体GUI受入はユーザーが行い、上記のうちAM-03、AM-05、AM-06、AM-08、AM-11をmouseとkeyboardで確認する。
自動試験の成功だけでGUI成功を宣言せず、GUI確認だけで状態遷移網羅を宣言しない。
